# 05 · Architecture and per-file optimisation rules

## 1. Process model

```text
dayz-launcher.exe (Tauri 2 / Rust)             msedgewebview2.exe ×6 (shared WebView2 runtime)
├─ tokio runtime (UDP A2S fan-out, HTTP, SQLite)   └─ Svelte 5 UI, one window, virtualised table
├─ Steam thread (steamworks Client; run_callbacks every 10 ms while a refresh or
│  unsubscribe runs, 100 ms otherwise — a download is looked at every 100 ms, D-295 —
│  and not at all while Steamworks is released or Steam is not running: the thread then
│  waits on its channel, D-164, D-275)
└─ launch: launch/process.rs spawns DayZ_BE.exe; launch_game awaits its exit on a
   blocking task and emits launch:exited
```

One window, no tray icon by default, no background service. Minimising does not pause anything: D-136 measured 0.2 % minimised against 0.02 % merely unfocused, so the window state is not the lever it looks like.

## 3. Data flow

1. Startup: the browser calls `servers_cached` → UI renders in < 100 ms. The rows come in columns since D-284: the field names once (`keys`, `tagKeys`) and one array per row, which `decodeCachedRows` turns into the store's one row shape (D-297). The row lifecycle then arrives on one ordered channel, the **row stream** (`send_rows` → `rows_subscribe`, D-297): `batch`, `dzsa-batch`, `done`, `pruned`, `verified`, `verify-done`, `mods-start`, `mods` and `mods-done`, each `{kind, data}`. Only `mods:progress`, `mods:done`, `steam:status` and `launch:*` are still events.
2. Steam thread: `internet_server_list(221100)` runs one request per partition (populated servers only at start-up; Refresh adds the empty ones, D-141) and streams `GameServerItem`s → a `batch` of at most 358 rows or 100 ms, whichever comes first (D-193). The DZSA fallback streams as `dzsa-batch` instead (D-271).
3. Verification: when a Steam refresh completes, the servers Steam listed as populated get A2S_PLAYER, plus INFO when their count is over 60 s old (D-047, D-237). The pass runs in its own 128-permit pool on the shared 400 datagrams/s pacer, with a 1 s timeout and one retry; a server that answers nothing gets a second look with INFO at 2.5 s (D-047). Servers still offline are read again 240 s later (D-268), and counted rows the listing did not reach are read again after the pass (D-247). Results leave as `verified` every 128 rows or 250 ms (D-193), and the store folds them into at most one recompute per 350 ms (D-164). On demand, up to 120 visible rows whose last check is over 120 s old (600 s for rows that could not be counted; never an R0 row) go to `servers_verify`, which reads INFO and PLAYER (D-272, D-281).
4. RULES: the details pane and the join read the server's live list. The mod lists behind the Mods column and the mod filter come from a scan after every verification pass: populated, modded servers whose stored list is missing or over a day old, leaving out those still waiting after a failed read, with 64 permits and a pacer of its own at 100 datagrams/s, one retry, in chunks of 200 (D-080, D-193, D-244). Its results stream as `mods`; the stored lists (`mods_index`) are loaded by the pages that need them when they open (D-284).
5. Join: RULES (or the stored list when RULES does not answer, D-209) → diff mods against the Workshop inventory → subscribe/download with progress → junctions → spawn.

## 4. IPC rules

- Commands are request/response; anything that streams uses **batched arrays**, never one message per server. Row data streams on the row stream, not as events: Tauri evaluates an event as a script with its JSON pasted in (`emit_js_script`), and the renderer kept every script it compiled — about 0.5 MB per 358-row batch, some 50 MB for minutes after a full Refresh. A channel message over 8 KiB is fetched and parsed as JSON instead, and the channel keeps the send order (D-297). An event is for something small and rare.
- A command that touches files, the registry, the network or the database runs off the main thread: `async fn`, or `#[tauri::command(async)]` for a plain one, which Tauri otherwise runs on the main thread (D-239, D-287).
- Server row payload: the camelCase form of `browser::ServerRow` — `{ id:"ip:qport", ip, gamePort, queryPort, name, map, description, players, maxPlayers, bots, password, serverVersion, version, pingMs, tags, verifiedPlayers?, steamEmpty?, verifiedAt?, verdict?, country? }`. Fields nothing renders are `skip_serializing` and absent options are omitted, which took a 19 000-row cold start from 15.05 MB to ~10.4 MB (D-164). Mod lists never ride on the row: they travel as `mods` on the row stream and through `mods_index`.
- Never send more than ~200 KB in one message; the WebView2 IPC bridge serialises to string. Rows go out 358 to an event (558 B each, `BATCH_MAX_ROWS`), verifications 128 (~314 B each), D-193, D-284.

## 5. Frontend state (Svelte 5 runes)

- `rows` is a plain `Map` keyed by `ip:queryPort` with one `$state` version counter (D-176); `list = $derived.by(…)` re-runs when a filter, the sort or the version changes. Batches are pooled and merged once every 350 ms (D-164), and verification results defer their recompute the same way.
- Virtual list: own component, fixed 36 px rows, renders viewport + 8 overscan rows; total DOM nodes stay < 1 000.
- The sort runs synchronously inside `list`, on packed integer keys through the engine's numeric sort: 4–17 ms per key at 40 000–71 000 rows (D-284). The name column sorts by ranks kept up to date as rows arrive, not by the collator on every recompute (D-181, D-284).
- No global stores library, no UI kit, no CSS framework; icons are inline SVG (§7 Assets).

## 7. Per-file optimisation checklist

Apply whenever a file of that type is created or patched; note deviations in [09-decisions-log.md](09-decisions-log.md).

### Rust (`*.rs`, `Cargo.toml`)
- `[profile.release]`: `opt-level = 3` (or `"s"` if size wins), `lto = "fat"`, `codegen-units = 1`, `panic = "abort"`, `strip = true`.
- Zero-copy parsing with `&[u8]` slices / `bytes::Bytes`; no `String` allocation per field unless it leaves the module.
- Bounded channels and semaphores for every fan-out; no unbounded `Vec` growth from network input (cap rules payload at 64 KB).
- `#[serde(rename_all = "camelCase")]` on IPC types; `skip_serializing_if = "Option::is_none"`.
- No `unwrap()` on I/O or network paths; typed errors with `thiserror`.
- Every parser has a unit test with the live fixture bytes captured by `tools/a2s_capture.js` (into `src-tauri/tests/fixtures/a2s`; `tools/a2s_probe.js` only prints).

### Svelte (`*.svelte`)
- Runes only (`$state`, `$derived`, `$effect`); no legacy stores.
- One component per concern; the table's rows are plain markup in `ServerTable.svelte`'s keyed `{#each}`, with no effects of their own.
- No layout thrash: read DOM sizes in one `$effect`, write in the next frame.
- `{#key}` blocks avoided in the row list; keyed `{#each}` by server id.

### CSS
- Design tokens as CSS custom properties on `:root`; themes switch by `[data-theme]`.
- System font stack (`"Segoe UI Variable Text", "Segoe UI", system-ui, sans-serif`): no web fonts shipped.
- `prefers-reduced-motion` respected; transitions ≤ 150 ms. `content-visibility: auto` is *not* used: the only long list is the virtualised table, which never puts off-screen rows in the DOM at all, and every other view is sized to fit without scrolling (D-094).
- No CSS framework; **gzip budget: < 10 KB** (8.4 kB at v0.1.23, after the Diagnostics page became the much smaller Logs page, D-168), raised from 8 kB with the reason recorded here. v0.1.19 was 7.7 kB across five views; the app now has nine, a mod manager, a video player and a log panel. The dedup lever described at v0.1.19 was pulled in v0.1.23 — the shared button base moved to `app.css` — and it recovered 1.3 kB raw but only **0.07 kB gzip**, because gzip already folds repeated rule blocks. The conclusion is that per-component scoped CSS costs almost nothing over the wire and the raw figure (48.3 kB at v0.1.23) is not worth optimising; the gate that actually matters is cold start to first paint, which is 0.43 s against a 1.0 s budget (D-164). **v0.1.37: 8.28 kB gzip** — down from 8.63 kB at v0.1.35 because D-226 deleted sixteen local `.btn` blocks and collapsed the chip radii, which is the first time the dedup lever has actually moved the gzip figure. JS the same release: **65.47 kB gzip** against 120. **v0.1.69: 9.48 kB gzip, 95 % of the gate** (JS 78.83 kB), D-287: the next page or restyle should look at the CSS it adds. **v0.1.72: 9.72 kB, 97 %** (JS 81.91 kB) after the accessibility round's focus rings, contrast-theme block and hidden text (D-291). **v0.1.78: 9.89 kB, 99 %** (JS 84.70 kB): the "What's new" window added 0.17 kB of CSS and 1.0 kB of JS (D-301). The next visible addition has to bring a saving with it or a reasoned raise of the gate. **v0.1.80: 9.93 kB, 99.3 %** (JS 87.14 kB): row 14's notices and the join window's fallback added 0.04 kB, and a scan found no global class unused. The gate is now full: the next page or notice needs a saving first, or a raise with its reason (the gate guards cold-start parse time, 0.43 s against the 1.0 s budget, D-164, not a download). **v0.1.83: 9.90 kB** (JS 90.41 kB): row 16 paid for its Open on chips, Record label and the open popover's border with the Direct connect crosshair's rules and the crash boxes' detail line (D-306). **Cache size and memory (D-310):** each 1 000 cached rows past 83 568 adds 0.32–0.41 MB to the whole app, so the 330 MB and 350 MB budgets hold to about 105 000 and 120 000 rows; D-309 keeps the cache near one listing (~35 000–50 000 rows). Population samples settle near 300 000 rows (~25 MB on disk) at the 7-day prune and are read per server only.

### TypeScript / Vite
- `build.target: "esnext"` (WebView2 is Chromium 153, no polyfills), `minify: "oxc"` (Vite 8 default; esbuild is not bundled, D-020), `sourcemap: false` in release.
- No runtime dependencies beyond `@tauri-apps/api` and its plugin bindings; check with `npm ls --omit=dev`.
- No route-level code splitting: it was specified at M0 and measured as not worth it at v0.1.23, where the whole app is one 200 kB chunk that parses in a few ms against a 427 ms cold start. Revisit if the bundle passes ~400 kB.

### Tauri (`tauri.conf.json`, `capabilities/*.json`)
- `app.withGlobalTauri: false`; the CSP in `tauri.conf.json` is `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob: https://i.ytimg.com; font-src 'self'; frame-src https://www.youtube-nocookie.com; connect-src ipc: http://ipc.localhost; base-uri 'self'; form-action 'none'; frame-ancestors 'none'`. The only third-party origins are the News page's video previews and player (D-150); `ipc:` and `http://ipc.localhost` are the bridge; `data:` covers the small images Vite inlines (the title bar's mark), `blob:` the news thumbnails' object URLs, and `'unsafe-inline'` the style attributes; `base-uri`, `form-action` and `frame-ancestors` are set explicitly because they do not inherit (D-163). Only the plugins used, each with the narrowest permission set: the updater may check, download and install, and notifications may ask for permission and notify — the three commands the notification plugin registers on desktop (D-287).
- `bundle.targets: ["nsis"]`, `windows.webviewInstallMode: { type: "downloadBootstrapper" }`, `nsis.installMode: "currentUser"`.
- Updater with a signing key pair; the public key committed, the private key never.
- Resources: `steam_api64.dll` only.

### Assets
- Icons are inline SVG in the component that uses them, the sidebar's included since D-250 (`RailIcon.svelte`; it used Unicode glyphs before); the sprite specified at M0 was never built, and with nine views carrying a handful of icons each it would cost more indirection than bytes. The app icon is the logo's gas mask, cut out and written at every size by `tools/make_icon.js` (D-258; it drew its own mark before, D-156), not `tauri icon`. Raster assets: the flag sprite, the mask in the title bar (3 KB, inlined) and the logo in the first-run dialog (45 KB, fetched only when it shows), D-258.

## 8. Security and privacy
- No telemetry and no accounts. Outbound traffic: Steam (Steamworks), UDP A2S to game servers, Steam's news feed and image CDN, GitHub for updates, the DZSA list when the user asks for it or, once at start-up, when Steam fails to initialise and the cached list is over an hour old (D-089, D-247), and YouTube for the News page's preview images and its embedded player. The installer downloads Microsoft's WebView2 bootstrapper when the runtime is missing. **The player is third-party remote code**, sandboxed and created only while a video is open (D-150/D-163); it is the one exception to "no remote code", and the news page can be switched off in Settings, and the installer offers the same choice before the launcher has ever run (D-206).
- Update artifacts are signature-checked by the updater plugin.
- The app's own folders are `%APPDATA%\<app>` (`settings.json`, `.window-state.json`) and `%LOCALAPPDATA%\<app>` (`cache.db`, `logs/`, `news-thumbs/`). Outside them the launcher only creates the `!Workshop` junctions in the game folder, deletes the setups its updater downloaded and left in `%TEMP%` (D-279), and deletes the installer's one-shot `DisableNews` value once it has applied it (D-206).
